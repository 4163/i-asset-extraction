# Contribute output pipeline

A structured workflow to publish verified asset extractions to public GitHub repositories and register them in the upstream catalog.

## Invocation

```text
/contribute-output <project_slug>
```

Example:
- `/contribute-output "genshin-impact-faruzan"`

---

## Core principles

1. **Non-destructive to workspace.** Never delete or modify files in the active `workspace/<project_slug>` directory. All staging occurs in `cache/export/<project_slug>`.
2. **Public community contribution.** Repositories generated by this skill are strictly public.
3. **Single pre-flight path assertion.** Scan `specs/`, `meta/`, and `gallery/` before staging to verify no absolute drive roots exist. Normalize any detected absolute links to relative paths.
4. **Immediate live gallery.** Deploy the visual gallery to GitHub Pages using static relative asset paths with zero backend dependencies.
5. **Reproducible toolchain attribution.** Catalog reverse engineering tools and custom scripts used during extraction in the exported README with upstream links. Upload proprietary tooling created during the workflow under `tools/` (or link to releases or dedicated tool repositories for heavy binaries).

---

## 4-Step workflow

### Step 1: Pre-flight audit and path hygiene check

Before staging files, verify project integrity and sanitize any remaining host paths:

1. Read `meta/state.json` and `meta/manifest.json`. Confirm Stage 4 visualization specification exists in `specs/visualization-spec.md`.
2. Execute a single regex search across `specs/*.md`, `meta/*.json`, and `gallery/index.html` for local drive roots such as `C:`, `D:`, `E:`, `G:`, `/home/`, or `file:///`.
3. If any local path is detected, replace it with a relative repository link or generic game title before copying to the staging directory.
4. Verify `gallery/index.html` uses relative static paths without dynamic streaming endpoints.

---

### Step 2: Mode resolution and alignment

Check whether the target repository already exists on GitHub or if `meta/state.json` records an existing publication URL:

- **Initial publication (new repository):**
  1. **Repository name.** Propose `<game-slug>-<entity-slug>-assets` under the user's authenticated GitHub account. Confirm the name.
  2. **Heavy asset distribution.** When compound assets exceed standard Git thresholds (such as multi-gigabyte animation clip folders), ask whether to track them via Git LFS or package raw animations into a compressed GitHub Release attachment to keep git clones light.
  3. **GitHub Pages activation.** Confirm deploying `gallery/` to GitHub Pages (`gh-pages` branch or root docs) so the live preview URL works immediately.
- **Repository synchronization (existing repository):**
  1. **Target repository.** Confirm the existing remote repository URL detected from project metadata.
  2. **Patch scope.** Confirm the game client version bump (such as `v7.1.0` to `v7.2.0`) and summarize added or modified assets.

---

### Step 3: Staging and repository publishing

Stage the export inside `cache/export/<project_slug>`:

#### Directory layout
```text
cache/export/<project_slug>/
├── .gitattributes          # Git LFS tracking rules for binary assets
├── .gitignore              # Standard ignore rules
├── README.md               # Human-readable repository overview
├── assets/                 # Filtered asset trees (audio, textures, meshes)
├── gallery/                # Self-contained visual confirmation gallery
├── meta/
│   ├── manifest.json       # Deterministic asset index and hashes
│   └── state.json          # Pipeline state and identity metadata
├── specs/                  # Stage deliverable documents
│   ├── mapping.md
│   ├── dependent-assets.md
│   └── visualization-spec.md
└── tools/                  # Proprietary or custom tooling created for extraction
```

#### Staging exclusions and tool preservation
Exclude ephemeral scratch scripts, raw download caches, and redundant files:
- Exclude one-off scratch scripts and temporary analysis logs.
- Preserve custom or proprietary extraction scripts and utilities created for the project under `tools/` so the repository remains self-contained.
- Exclude virtual hash folders containing redundant duplicates already organized in Stage 3.

#### Static gallery audio playback
GitHub Pages serves static files only. In `gallery/index.html`, point all audio tracks to relative static paths and never reference backend endpoints (`/stream-audio`). Proprietary formats (`.wem`, `.fsb`) decode client-side via the embedded WebAssembly engine.

#### README generation guidelines
All template categories, technical fields, and tool entries below are non-exhaustive examples to guide structure rather than rigid boundaries. Agents must adjust them dynamically to reflect the actual target project, omitting unused rows and populating verified data:
- **Asset overview:** Include only categories containing extracted files.
- **Technical specifications:** Document the verified engine structures, skeleton hierarchies, or material parameters discovered in the workspace.
- **Toolchain attribution:** Catalog only tools and utilities actually used during extraction.
- **Proprietary and custom tooling:** Upload custom scripts or proprietary tools created during extraction into `tools/` and link to `[tools/<tool_name>](tools/<tool_name>)`. For tooling binaries exceeding GitHub file limits, attach them to a GitHub Release or create a separate tool repository dump with an initial generic README (for multi-file or multi-architecture tools) so the table links directly to them.
- **Disclaimer:** Attribute asset ownership to the game publisher and state the archival purpose.

#### Git execution
- **Initial publication:**
  1. Initialize a git repository in the staging directory.
  2. Commit all staged files.
  3. Create the public repository with automated description and website URL:
     ```bash
     gh repo create <repo-name> --public --source=. --remote=origin --push --description "Extracted assets, technical specifications, and interactive gallery for <Entity Name> (<Game Title>)" --homepage "https://<user>.github.io/<repo-name>"
     ```
  4. Deploy `gallery/` contents to GitHub Pages using `gh-pages` branch or repository settings.
- **Repository synchronization:**
  1. Clone or fetch the existing remote repository into `cache/export/<project_slug>`.
  2. Overlay updated assets, specs, manifests, and rebuilt gallery.
  3. Update `README.md` version badges and asset counts, and append a concise summary under `## Version history`.
  4. Update repository metadata via `gh repo edit --homepage "https://<user>.github.io/<repo-name>"`.
  5. Commit with message: `feat(update): sync <entity> assets for <version>`.
  6. Push to `main` and trigger GitHub Pages redeployment.

> [!NOTE]
> GitHub does not expose an API endpoint for the "Include in the home page: Packages" checkbox in repository sidebar settings. Unchecking Packages must be toggled manually in the repository About dialog if desired.

---

### Step 4: Upstream catalog registration

After publishing or updating the repository, synchronize the central registry:

1. Clone or fetch `https://github.com/4163/i-asset-extraction`.
2. Locate the `Community extractions` table in its `README.md`.
- **For initial publication:**
  Append a new row to the table:

```markdown
| Game | Entity | Version | Repository | Assets | Contributor |
|---|---|---|---|---|---|
| <Game Title> | <Entity Name> | <Version> | [<repo-name>](https://github.com/<user>/<repo-name>) | <Count> | [@<user>](https://github.com/<user>) |
```

  Create branch `add-<project_slug>` and run `gh pr create` with a summary of the new extraction.
- **For repository synchronization:**
  Locate the existing row matching `<Game Title>` and `<Entity Name>`. Update the `Version` and `Assets` count cells in place.
  Create branch `update-<project_slug>-<version>` and run `gh pr create` titled `chore(catalog): update <Entity Name> to <version>`.
